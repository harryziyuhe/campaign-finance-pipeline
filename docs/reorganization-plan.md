# Reorganization Plan

This plan is intentionally non-destructive. It recommends a target structure and a staged migration path, but does not require moving or removing any current files immediately.

## Goals

1. Make the active pipeline obvious.
2. Separate source data, generated intermediates, curated inputs, and final outputs.
3. Reduce machine-specific paths and manual script editing.
4. Preserve legacy scripts while making their status explicit.
5. Make every major output traceable to the script that generated it.

## Data Layering Rule

Use a simple provenance rule for all future files:

| Layer | Meaning | Examples |
| --- | --- | --- |
| `data/raw/` | Downloaded or scraped source files that should not be manually edited. | FEC bulk `.txt`, raw FEC API JSON/CSV, Inside Elections XML, raw LSEG pulls. |
| `data/external/` | External or manually curated inputs that are not generated by the pipeline. | `house_general_cands.csv`, industry classifications, hand-coded firm matches. |
| `data/interim/` | Reformatting or partially processed files that are useful checkpoints but not final analysis inputs. | Bulk FEC parquet conversions, intermediate corporate PAC matches, market-return read logs. |
| `data/processed/` | Stable analysis inputs produced by scripts. | `firm_pac_to_candidate_contributions.parquet`, `house_firm_cand.parquet`, `cand_model_data.RDS`. |
| `outputs/` | Final artifacts for papers, talks, or reporting. | model `.RDS` files, figures, LaTeX tables, result logs. |

## Staged Migration

### Stage 1: Document and Freeze Conventions

Do this before moving files:

1. Keep the current layout unchanged.
2. Add `docs/repo-map.md`, `docs/reorganization-plan.md`, `docs/runbook.md`, and `docs/data-dictionary.md`.
3. Add script status headers to active scripts.
4. Add a root path configuration file and update only one or two active scripts as proof of concept.
5. Define canonical outputs for the current paper/project.

### Stage 2: Centralize Paths

Create one path resolver rather than embedding `S:/campaignfinance/` everywhere.

Recommended Python pattern:

```python
from pathlib import Path
import os

PROJECT_ROOT = Path(os.environ.get("CAMPAIGNFINANCE_ROOT", Path(__file__).resolve().parents[2]))
DATA_DIR = Path(os.environ.get("CAMPAIGNFINANCE_DATA", PROJECT_ROOT / "data"))
OUTPUT_DIR = Path(os.environ.get("CAMPAIGNFINANCE_OUTPUTS", PROJECT_ROOT))
```

Recommended R pattern:

```r
project_root <- Sys.getenv("CAMPAIGNFINANCE_ROOT", unset = normalizePath("../.."))
data_path <- file.path(project_root, "data")
model_path <- file.path(project_root, "models")
```

This can be introduced without moving any data. It also makes scripts runnable on Windows, WSL, Linux, or another drive.

### Stage 3: Add Thin Command-Line Entrypoints

Current scripts often require editing comments at the bottom of the file. Replace that with CLI arguments while preserving the existing functions.

Examples:

```text
python scripts/FEC/FECscraper.py candidates --office H --start-year 2004
python scripts/FEC/FECprocessor.py aggregate-candidate-contributions
python scripts/aggregate/HouseData.py --scope election-year
python scripts/LSEG/EventStudy.py --config config/lseg-data.config.json
```

The immediate benefit is reproducibility: a runbook can list exact commands.

### Stage 4: Split Notebooks from Production Scripts

Keep notebooks, but make their role clear:

| Current pattern | Recommended convention |
| --- | --- |
| `scripts/FEC/analysis_2024.ipynb` | `notebooks/fec/analysis_2024.ipynb` or `scripts/notebooks/fec/analysis_2024.ipynb`. |
| Notebook creates canonical data | Promote the relevant cells into a Python/R script and keep the notebook as a view/report. |
| Notebook used for inspection only | Mark as exploratory in a notebook index. |

### Stage 5: Migrate Data Gradually with Compatibility Shims

When ready to move data, do it by adding a manifest first:

```csv
old_path,new_path,owner_script,status,notes
data/FEC/raw,campaignfinance/data/raw/fec_bulk,FECtidy.py,planned,bulk downloaded files
data/FEC/API,campaignfinance/data/raw/fec_api,FECscraper.py,planned,FEC API outputs
data/FEC/processed,campaignfinance/data/processed/fec,FECprocessor.py,planned,processed FEC tables
data/market/returns,campaignfinance/data/raw/lseg/returns,Stockscraper.py,planned,per-ticker returns
```

Then update scripts to use the manifest or path resolver. Only after all active scripts read from the new locations should old files be archived or removed.

## High-Value Fixes Before Any Move

These changes are low-risk and will improve trackability immediately:

1. Add `.gitignore` if the repo is put under Git. Ignore `.venv/`, `.ruff_cache/`, `__pycache__/`, `.DS_Store`, `._*`, logs generated by runs, and optionally large generated outputs.
2. Replace hard-coded root paths in active scripts with a shared root resolver.
3. Fix `scripts/analysis/cand_model.R` output path from `model/` to `models/` or create an explicit config value.
4. Replace interactive prompts in `scripts/aggregate/HouseData.py` with CLI flags so runs can be reproduced.
5. Add an output manifest for each active script with input files, output files, and expected refresh cadence.
6. Move API keys out of scripts and into environment variables or ignored local config files.

## Proposed Run Order to Document in a Runbook

Use this as the starting point for `docs/runbook.md`:

1. Refresh FEC API candidate and committee metadata.
2. Reformat FEC bulk files and update corporate PAC mappings.
3. Build processed FEC contribution tables.
4. Refresh LSEG firm metadata and market returns if needed.
5. Run market event/exposure scripts.
6. Refresh election ratings if source ratings changed.
7. Build House candidate-level analysis panels.
8. Build R modeling datasets.
9. Estimate models.
10. Generate figures and tables.

## Naming Conventions for New Files

Use consistent names for future outputs:

| Object | Recommended pattern |
| --- | --- |
| Raw per-cycle source file | `{source}_{entity}_{cycle}.{ext}` |
| Processed panel | `{unit}_{measure}_{scope}.parquet` |
| Model data | `{unit}_model_data_{scope}.RDS` |
| Model object | `{outcome}_{spec}_{scope}.RDS` |
| Figure | `{figure_number_or_topic}_{scope}.{png|pdf}` |
| Table | `{table_number_or_topic}_{scope}.tex` |

Examples:

```text
data/processed/house/house_firm_candidate_all.parquet
data/processed/house/house_firm_candidate_election_year.parquet
outputs/models/election/contribution_logit_baseline.RDS
outputs/figures/conditional_contribution_probability_2018.png
```

## Decision Points

Before doing actual file migration, decide:

1. Whether `models/`, `figs/`, `tables/`, `logs/`, and `results/` should stay top-level or move under `outputs/`.
2. Whether large generated data should stay in the repo, be ignored by Git, or move to an external data store.
3. Which scripts are canonical for the paper and which are historical.
4. Whether the repo should support both Windows paths and WSL/Linux paths.
5. Whether FEC API refreshes should be full-refresh, incremental, or date-stamped snapshots.
